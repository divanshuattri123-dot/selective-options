# Runtime funding poll proof

Version 0.3.27 adds the optional `BinanceFundingCollector` to supervised capture. It starts only when enabled. Each asset downloads an explicitly bounded rolling window, stages the whole discovery/page plan, verifies its exact scope and canonical observations, then publishes observations followed by poll health. Access, API/rate and transport failures abort the cycle before another asset request; invalid asset data records failure and allows the next asset. Every cycle pauses for the configured interval, including failures. No immediate retries occur. Consumer/storage errors and cancellation propagate; interruption during publication may leave some accepted rows without completed health. Health receipt means sink acceptance, not an atomic commit guarantee.

`collect_once.py` performed one supervised BTC poll through the new adapter, using page size two. Five public requests returned six funding observations across four history pages, ending empty. Six point-in-time checks, exact replay, seven outbox rows, sealed export and closed canonical reload passed. The database contains six funding rows and one success health row. Collection stopped. No scheduling loop, private API, order or long-running soak was started.

`verify_saved.py` compares exact saved public values/receipts, twelve SQL before/at-receipt boundaries, database/Parquet equality and unchanged source bytes. It replays the saved responses through the current runtime adapter without network and reproduces all seven original rows exactly. A later poll with clearly synthetic receipts and a simulated 429 outage add eight labelled synthetic rows. Fifteen fixture rows/outbox entries survive exact replay and sealed export. SQL selects six charges from twelve funding observations; the original seven-row view remains unchanged, and the latest failure health remains visible. Synthetic receipts/outage are not evidence of an actual later venue poll or rate limit.

Both scripts preserve existing databases and refuse to overwrite completed evidence. Reproduce in a fresh sibling copy of this folder with saved source files; the independent verifier needs the project's Python environment. The fixture verifier makes no network requests. The public collector does one finite new download when explicitly run. `report.json` and `verification.json` distinguish actual source evidence from simulation.

Default rolling window is 48 hours with a 900-second pause (minimum 600), per-asset deadline 90 seconds, page size 200 and ten history pages. History intervals, first publication and complete schedules remain unknown. Repair only covers the requested window; older gaps, archive rotation, long-running deployment, cross-asset/cross-venue coverage and full-source restart remain unfinished. Capture exposes canonical revision views, latest recorded poll outcomes (including tied receipts), and separate health receipt freshness. These diagnostics never approve trading.
